# 任务契约与验收闭环（第一版）

本版针对“反复反馈不能用，但 AI 只重复编译并声称完成”的问题，增加独立于模型摘要的需求记录和运行时验收状态。它适用于一般编程任务，没有贪吃蛇专用判断。

## 已实现

- 在项目状态目录 `.webcool_agent/task-contract-<session-id>.json` 持久化用户原文，编号 U1、U2……。无会话运行按 run ID 隔离。原始要求与后续反馈一起进入每次模型请求，压缩工具上下文不删除契约；恢复同一请求不重复追加。
- 老会话首次升级只导入仍保留的用户消息，明确标记历史可能不完整，不把模型摘要当作用户原话。最多 64 KiB 用户原文、256 条、128 KiB 编码后契约；超限或文件损坏明确失败，不静默删减要求。
- 提示模型先把需求映射为可观察行为，区分证据、推测和未知；重复失败反馈应先复现实际症状，检查输入、状态、输出完整路径。后续明确修订可覆盖旧要求；一般“仍不能用”不能抹掉原任务。
- 普通实现任务通过固定检查后增加至多一次验收复核机会，要求补查未覆盖行为或明确无法执行的验证。编译修复和仅运行验证的任务保留快速结束路径，额度不足时直接交付验收限制，不追加无限验证循环。
- 固定验证报告包含实际源码快照指纹、提案指纹、私有草稿沙箱范围、网络策略及各命令结果。报告来自运行时验证器，不接受模型文字作为通过证明。结束时比较当前版本，版本变化使证据失效；新一轮不继承旧证据。
- 最终结果持久化 `task_contract_json`、`task_acceptance_json` 和 `task_acceptance_status`，运行状态接口返回相同字段。结果仍采用原来的 completed 生命周期；验收独立判断，避免破坏文件审查和恢复协议。
- 界面与会话摘要明确“检查通过，功能待验收”“验证失败”或“编译修复已验证”。每条用户请求的覆盖状态均可见于 `requirement_coverage`。

## 状态含义

| 状态 | 含义 |
| --- | --- |
| pending_verification | 没有当前版本的有效验证证据，或未执行检查 |
| checks_passed | 当前版本已配置检查通过，用户要求尚未逐项证明 |
| verification_failed | 当前版本执行的检查失败 |
| scope_verified | 明确的编译修复范围已验证；相关测试告警仍保留，不代表其它需求完成 |

报告是本轮结束时的历史证据。应用提案、手动修改文件、修改运行环境之后应重新验证。审查文件的 accepted/rejected 与功能验收无关。失败运行保留需求契约与操作日志；成功交付的结果文件另保存验收快照。

## 第一版边界

需求原文是契约的权威部分。本版通过提示要求模型拆解验收条件，但尚未把模型拆解出的细粒度条件作为独立、可编辑的结构化计划持久化，也不自动证明测试覆盖所有自然语言要求。因此 `all_user_requirements_verified` 保持 false，不能仅凭生成一份测试或测试全绿升级为业务验收成功。

复用现有编译、测试、HTTP 和配置的功能验收检查；没有新增通用浏览器操作器。没有浏览器交互证据时，游戏可见、键盘控制、多人状态等仍待验收。复核最多多一轮交接机会，之后模型仍受原工具预算与无进展控制约束。下一步可在这套可信状态之上增加可审查的逐项验收条件、测试覆盖映射和浏览器验证适配器。

## 验证方式

- `python3 webcool/tests/compile_repair_http_test.py --task-contract`：真实 HTTP 运行、临时项目和模拟提供商；通过检查后一次复核，模型声称全部完成也不能自证；后续“仍不能用”保留原始要求并失效旧证据；API 与持久化结果一致。
- `--task-contract-stale` 额外模拟验证结束后正式源码被外部修改，确认旧证据不可作为当前验证。
- 原有编译修复、自动构建、失败收敛、上下文压缩、仅验证、批次后修改与调查额度回归。
- CMake `ai_common_primitives`：状态决策、恢复幂等、身份校验、容量限制、损坏记录不覆盖；另运行静态库链接与编译修复范围测试。

## 任务总结与验证结论分离

任务总结不再被验收状态覆盖。它按“本轮需求原文、实际文件修订、AI 处理说明、验证结论”组织。需求不使用只保留第一句话的会话标题，因此多项功能要求会一起展示。模型提供的实施说明和未完成项保留并标注来源；没有说明时只陈述可确认的文件操作，不根据文件名推测功能已实现。验收状态仍独立由运行时计算。总长度保留在结果存储的 4 KiB 限制内，各部分分别预留空间，长需求完整原文仍保存在任务契约中。

## 逐项需求完成程度

最终协议增加 `requirement_progress` 数组，每项为 requirement、status（implemented/partial/not_implemented/unknown）、evidence 和 remaining。要求模型拆开复合需求，分别报告实施程度及依据，不以文件数或编译结果推断功能完成。运行时限制条数和字段长度；缺少依据的“已实现/部分完成”降为无法确认，拒绝未知状态和模型自行提供的已验收标记。

总结优先展示每项“已实现，待验收 / 部分完成 / 未完成 / 无法确认”，并保留待办。完整规范化报告保存在验收 JSON 的 requirement_progress_json，来源明确为模型报告，independently_verified 保持 false。验证器快速结束或模型未提供报告时，明确显示“无法确认”，不编造完成率，也不额外启动无界总结循环。
